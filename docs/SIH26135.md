# SIH26135: from training records to livelihood journeys

Official statement: https://sih.gov.in/sih2026PS — search for **SIH26135**.

Udaan Atlas addresses the gap between training completion records and reliable, continuing information about employment, self-employment, income, and barriers to lasting work.

## Requirements and implemented behavior

| Statement need                                        | Working feature                                                                                                                          |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Consent-based trainee records                         | Enrollment consent, scoped passport, withdrawal transition, contact suppression                                                          |
| Longitudinal follow-up                                | Outcome timeline and 30/90/180/365-day milestones                                                                                        |
| Employment and self-employment outcomes               | Six explicit outcome states, pay, role, employer, date, and notes                                                                        |
| Employer information validation                       | Linked-account review of an exact outcome; source and discrepancy history                                                                |
| Wage and retention progression                        | Income timeline, paired baseline/current change, and defined 90-day work-continuity measure                                              |
| Automated and assisted follow-ups                     | Automatic milestone creation, explainable due queue, copyable optional check-ins, assisted update forms; no unattended external delivery |
| Skill gaps and non-placement/attrition reasons        | Reported missing skills, notes, explicit “Seeking work” and “Left job” states                                                            |
| Course/provider/district/cohort/demographic analytics | Filtered dashboard and contextual impact report                                                                                          |
| Low-burden, privacy-conscious collection              | Short forms, consent checks, minimum relevant data, scoped accounts, and separate demo/private modes                                     |

## The idea to demonstrate

The product's differentiator is the connection between **a person’s longitudinal passport**, **claim-specific evidence**, and **an explainable support step**.

A placement count does not finish the story. A new outcome does not inherit old verification. Missing contact is not labeled unemployment. A low skills match is not treated as a prediction of someone's potential.

## Five-minute walkthrough

1. Open the big picture. Filter Pune and Solar Installation. Explain the denominator and the distinction between a current work outcome and employer-confirmed evidence.
2. Open a learner passport. Follow the training date, reported work, evidence, and support reasons.
3. Record a new outcome. Point out that confirmation starts fresh for the new claim.
4. In the public demo, switch to Employer. Review a linked record, record a confirmation or mismatch, and see the evidence label change. Private mode enforces that binding on the server.
5. Open the follow-up studio. Work through a due milestone, record an assisted check-in, and schedule skill support.
6. Open Skill radar. Show the exact missing skills in an employer-entered role. Add an opportunity to make the comparison change.
7. Switch to Learner. Submit an optional update and show consent controls.
8. Open the impact report. Explain why observed income change does not prove causal impact, then export the filtered CSV.

Use only fictional records in a public demonstration. The starter names, employers, providers, and outcomes are synthetic examples.

## Support-priority rules

| Signal                            | Contribution                                      |
| --------------------------------- | ------------------------------------------------- |
| No outcome                        | +35                                               |
| Latest report says “Left job”     | +40                                               |
| Latest report says “Seeking work” | +22                                               |
| At least one overdue milestone    | +15, then +1 per five days overdue, capped at +35 |
| Latest update older than 90 days  | +20                                               |
| Reported missing skills           | +5 per skill, capped at +15                       |
| Latest evidence has a mismatch    | +20                                               |

Total is capped at 100. Scores of 65 or more are labeled “Act now,” 30–64 “Check in,” and lower scores “On track.” Every reason is displayed. These thresholds are prototype defaults to validate with programme staff, not statistically validated predictions. Protected characteristics and income are not inputs. Staff make the final support decision.

## Evidence semantics

Each evidence event refers to one `outcomeId`. It records the reviewer, reviewer type, verdict, timestamp, and note. The latest evidence event determines the displayed review state for that exact claim. A later team review can change the claim’s current display to “Team reviewed”; it does not masquerade as employer confirmation. The complete prior evidence history remains visible.

## Technical and deployment boundaries

The public site is a static, interactive demonstration. The repository also contains a private same-origin server with SQLite persistence and account permissions. An actual multi-organization deployment will need tenant isolation, normalized storage, institutional onboarding, recovery procedures, background scheduling, and governance appropriate to the operating programme.

Government verification and messaging services are integration points, not assumed connections. Build adapters only against officially authorized interfaces. Tests should use synthetic data and provider sandboxes.
